# 계획: 보호자 사진 전송과 알림장 (구현 전 검토용)

> 상태: **M1(인증)·M2(기록에 사진 첨부) 구현 완료**, M3~M5와 2차 항목은 아직 구현되지 않았습니다. (구현 내용은 README 참고)
> 결정된 사항은 **9장**에 모았습니다. 구현은 9장의 남은 확인 사항이 정해진 뒤 단계별로 진행합니다.

## 1. 왜 필요한가

조사한 다른 유치원의 일과표에는 "생활사진·영상 전송(키즈노트)"이 **일과의 정식 항목**으로 들어 있습니다(점심·휴식 시간, 저녁 식사 시간, 호텔의 아침 인사·굿나잇 사진).
직원 입장에서는 사진을 메신저로 따로 보내는 일이 곧 추가 업무이고, 어떤 보호자에게 이미 보냈는지도 놓치기 쉽습니다. 이 프로젝트의 핵심 질문과 같은 구조입니다.

> 기록 → (직원이 확인·승인) → 보호자에게 전달 → 전달 여부를 직원이 한눈에 확인

그래서 별도 기능으로 붙이지 않고, **이미 있는 기록·승인·일과 흐름 위에** 올립니다.

## 2. 범위

| 구분 | 내용 |
|---|---|
| **1차(이번에 만들 것)** | 기록에 사진 첨부 → 직원 공개 승인 → 보호자 알림장에서 확인 / 보호자 이메일 로그인 / 일과 구간의 "사진 공유 시점" 표시 / 퇴원 처리와 3개월 후 자료 삭제 |
| **2차** | 짧은 영상 업로드(최소 제한), 반 전체 앨범(사진별 공개 대상) |
| **범위 밖(명시)** | 푸시·이메일 알림, 카카오 연동, 비밀번호 재설정 메일, 결제, 댓글·좋아요, 실시간 채팅, 보호자 프로필 사진 |

> 주의: 알림을 보내지 않으므로 보호자는 앱(웹앱)을 열어야 사진을 볼 수 있습니다. 대신 앱 안에서 **"새 알림장 N건" 표시**로 놓치지 않게 합니다. 이것은 실제 푸시가 아니며, 화면에도 알림이 전송된 것처럼 표시하지 않습니다.

## 3. 사용자 흐름

**직원**
1. 기록 작성 시 사진 첨부(여러 장 가능, 어느 아이가 찍혔는지 태그)
2. 기록 상세에서 *보호자 공개 승인* → 보호자에게 보일 문구와 **공개할 사진을 직접 선택**
3. 일과 화면에서 "이 구간에 아직 사진을 못 받은 보호자"를 확인

**보호자**
1. 직원이 보낸 초대 코드로 가입(이메일·비밀번호) → 자기 아이에게만 연결
2. 알림장 피드: 날짜별로 승인된 문구와 사진 확인, 사진 크게 보기·저장
3. 내부 메모, 업무 인계, AI 초안, 승인 전 사진은 **절대 보이지 않음**

## 4. 데이터 모델 (추가)

기존: `organizations`, `staff`, `dogs`, `care_records`(공개 상태·문구 포함), `routine_blocks`, `tasks` …

```
accounts        id, org_id, email(unique), name, password_hash, role('staff'|'parent'), staff_id?, created_at
                -- 보호자는 이름과 '누구의 보호자인지'(guardian_dogs)만 있으면 됨. 프로필 사진 없음
guardian_dogs   account_id, dog_id                      -- 보호자 ↔ 반려견 연결(다대다)
invites         code(해시 저장), org_id, dog_id, expires_at, used_at
media           id, org_id, record_id, kind('photo'|'video'), path, width, height, bytes,
                uploaded_by, created_at
media_dogs      media_id, dog_id                        -- 한 사진에 여러 아이 태그
media_shares    media_id, dog_id?, scope('dog_guardians'|'class_album'), approved_by, approved_at
```

- 승인 전 `media`는 직원에게만 보입니다. 공개는 **`media_shares` 행이 있을 때만** 가능합니다(기본 비공개).
- 기존 `care_records.parent_status/parent_text` 승인 흐름을 재사용하고, 사진 선택만 추가합니다.
- `routine_blocks`에 `share_prompt`(사진 공유 시점 여부) 컬럼을 추가합니다.
- `dogs`에 `discharged_at`(퇴원 시각), `purge_after`(자료 삭제 예정일 = 퇴원 + 3개월), `consent_at`(보호자 동의 기록 시각)을 추가합니다.

## 5. 인증과 권한

- 비밀번호는 표준 라이브러리 `hashlib.scrypt`(또는 argon2)로 **해시만 저장**, 솔트 사용. 로그인 시도 횟수 제한.
- 세션은 `HttpOnly`·`SameSite=Lax` 쿠키, 상태 변경 요청에 CSRF 방어.
- 보호자 가입은 **직원이 만든 초대 코드**로만 가능(코드는 해시 저장, 만료·1회용). 아무나 가입해서 다른 집 아이를 연결할 수 없게 합니다.
- 현재의 `X-Staff-Id` 헤더 방식은 직원도 같은 로그인으로 **교체**합니다. 데모 모드(드롭다운 전환)는 `DEMO_MODE=1`일 때만 남겨 포트폴리오 시연은 그대로 가능하게 합니다.

| 행동 | 직원 | 보호자 |
|---|---|---|
| 사진 업로드·태그·삭제 | ✅ (같은 유치원) | ❌ |
| 공개 승인·취소 | ✅ | ❌ |
| 승인된 자기 아이 알림장 열람 | ✅ | ✅ (연결된 아이만) |
| 다른 아이의 사진·기록 | ✅ (같은 유치원) | ❌ |
| 업무·내부 메모·AI 초안 | ✅ | ❌ |

## 6. 개인정보와 안전 (가장 신경 쓸 부분)

| 위험 | 대응 |
|---|---|
| **사진 주소만 알면 누구나 열람** (현재 프로필 사진 방식) | 보호자 사진은 로그인 + 권한 확인을 거치는 경로로만 제공. 공개 주소로 두지 않음 |
| 다른 집 아이·사람이 함께 찍힌 사진 | 사진별 태그 + 공개 대상(해당 보호자만 / 반 전체). 반 전체 앨범은 **2차**에서 별도 확인 절차 |
| 사진 속 위치 정보(EXIF) | 업로드 시 EXIF 제거(브라우저에서 다시 그려 저장, 서버에서도 검증) |
| 형식 위조·악성 파일 | 지금의 형식·용량 검사 유지, 영상은 허용 형식·길이·용량 제한 |
| 잘못 공개한 사진 | 공개 취소 즉시 보호자 화면에서 사라짐, 삭제 시 파일도 제거 |
| 보관 | **퇴원 처리 후 3개월**이 지나면 삭제(유치원·호텔 동일). 보호자 동의는 약관 단계에서 받는다고 가정하고, 프로토타입은 동의 기록 시각만 저장 (아래 '퇴원과 자료 삭제' 참고) |
| 법적 검토 | 실제 서비스 전환 시 개인정보 처리 방침·동의 절차는 별도 검토 필요(이 프로토타입은 가상 데이터만 사용) |

### 퇴원과 자료 삭제 (결정 반영)
- 직원이 반려견 프로필에서 **퇴원 처리**하면 `discharged_at`과 `purge_after`(+3개월)가 기록됩니다.
- 삭제 예정일이 지나면 해당 반려견의 **사진·영상 파일과 보호자 연결**을 삭제합니다. 삭제 전에는 "삭제 예정일"을 보여주고, 삭제 후에는 되돌릴 수 없다고 표시합니다.
- 프로토타입에는 실제 예약 작업(스케줄러)이 없으므로 **관리자의 "삭제 대상 정리 실행" 버튼**과 서버 시작 시 점검으로 구현합니다. 시간이 지나면 저절로 삭제되는 서비스처럼 표현하지 않습니다.

## 7. 일과와의 연결

- 일과 구간에 "사진 공유 시점" 표시(예: 점심·휴식, 하원 준비). 해당 구간 화면에 **"오늘 사진이 아직 공개되지 않은 반려견"** 목록.
- 조사한 일과표처럼 **유치원과 호텔은 하루 구성이 다릅니다**(호텔은 저녁 식사·배변·입실 전 체크 같은 야간 구간이 있음). 일과 템플릿을 유치원/호텔 중 고를 수 있게 할지는 9장의 확인 사항입니다.

## 8. 단계별 계획과 완료 기준

| 단계 | 내용 | 완료 기준(검증 방법) |
|---|---|---|
| **M1 인증** | accounts, 로그인/로그아웃, 세션, 초대 코드, 직원 인증 전환 + 데모 모드 | pytest: 잘못된 비밀번호·만료/재사용 초대·다른 유치원 접근 거부 / e2e: 로그인 후 새로고침 유지 |
| **M2 미디어 업로드** | 기록에 사진 첨부·태그, EXIF 제거, 권한 있는 제공 경로 | 형식 위조·용량·경로 조작·타 유치원 접근 거부 테스트 |
| **M3 공개 승인** | 승인 모달에서 사진 선택, `media_shares`, 취소 | 승인 전 보호자 응답에 사진이 **없음**을 테스트로 확인 |
| **M4 보호자 알림장** | 보호자 로그인 화면, 연결된 아이만 피드, 사진 보기 | 보호자 A가 보호자 B 아이 사진을 요청하면 404/403 |
| **M5 일과 연결** | 사진 공유 시점, "미공개 반려견" 현황 | e2e: 승인하면 현황에서 사라짐 |
| 2차 | 영상, 반 앨범, 이메일 알림 | 별도 계획 |

각 단계는 **실행 가능한 상태로 커밋**하고, 실제 실행한 테스트만 결과로 보고합니다.

## 9. 결정 사항 (모두 확정)

| 항목 | 결정 |
|---|---|
| 보호자 프로필 | 사진 없음. 이름과 "누구의 보호자인지"만 |
| 로그인 | 이메일 + 비밀번호, 직원이 만든 초대 코드로만 가입 |
| 사진 첨부 | 한 번에 최대 10장. 브라우저에서 긴 변 1600px로 줄여 올리고, 서버 상한은 장당 2MB |
| 영상 | 1차에서는 만들지 않음. 2차에서 짧은 길이·작은 용량으로 최소 구현 |
| 저장 위치 | 서버 디스크(`uploads/`). 외부 저장소는 범위 밖 |
| 퇴원·삭제 | 퇴원 처리 후 **3개월** 뒤 삭제(유치원·호텔 동일). 보호자 동의는 사전에 받는다고 가정하고 동의 시각만 기록 |
| 퇴원 직후 보호자 접근 | 3개월 동안 이미 공개된 사진은 볼 수 있게 유지하고, 새 사진은 올리지 않음. 삭제일에 함께 삭제 |
| 삭제 범위 | **사진·영상 파일과 보호자 연결만** 삭제. 글로 된 돌봄 기록과 업무 이력은 유지 |
| 알림 | 이메일·푸시 없음. 앱 안의 "새 알림장 N건" 표시만 |
| 일과 템플릿 | 1차는 유치원 템플릿 하나. 호텔형 선택은 2차 |
| 호스팅 | 1차는 본인 컴퓨터에서 실행하고 캡처·시연 영상으로 공개. 인터넷 공개 배포는 별도 결정 |

다음 단계는 **M1(인증)** 입니다.

## 10. 이 프로토타입에서 하지 않는 것

실제 보호자 개인정보·반려견 사진의 사용, 결제, 푸시 알림, 카카오 연동. 모든 데이터는 계속 **가상**입니다.
